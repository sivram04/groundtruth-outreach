# Playbook upload / review / select / preview — 2026-10-01

Milestone: a founder uploads a PDF or DOCX playbook, inspects the extracted text and the identified
initial-email, follow-up and timing rules, sees what is missing or ambiguous, selects an immutable version
by its content hash, and previews a candidate from it — all **flag-gated (`enable_playbook`, off by default
and in deploy), local, read-only**. No Gmail draft, no send, no live Sheet/Drive write; the Drive handbook
stays authoritative for production.

## What is built

- `outreach/playbook_extract.py` — extract text from a PDF (`pypdf`) or DOCX (`python-docx`), local libraries
  only. Explicit rejection reasons: `empty`, `too_large` (> 5 MB), `unsupported` (not .pdf/.docx),
  `malformed` (corrupt/parse error), `no_text` (image-only/scanned), `too_long` (> 60,000 chars).
- `outreach/playbook.py` — `review(text)` parses the handbook text into the initial-email section, the
  follow-up sections (reusing `followup.templates`), the timing rule (business-day counts), the offer values,
  and the missing/ambiguous lists. `content_hash(text)` is the immutable version id (same normalisation the
  Drive handbook uses). Pure; the text is parsed by regex as data only, never run as instructions, never sent
  to a model.
- `outreach/console.py` (under `enable_playbook`): `POST /api/playbook/review` (multipart upload → extract →
  review, read-only) and `POST /api/playbook/preview` (selected text + content hash + a first name → a
  follow-up candidate via the existing `followup.render` boundary). The preview **refuses with 409 if the
  posted text no longer hashes to the selected version** — a changed file must be reviewed and selected again.
- Frontend: a flag-gated **Playbook** page (`console/src/pages/Playbook.tsx`, nav gated by
  `snapshot.playbook_enabled`): upload → shows the extracted text (as plain data, never rendered as HTML) and
  the found/missing/ambiguous sections → "Select this version (<hash8>)" → preview follow-up 1 for a sample
  recipient. Rejected files show their reason.

## The durable-selection blocker (why this is bounded, not the full milestone)

Durable, cross-session **selection** would mean persisting the selected playbook *text* so the preview works
after a reload. The only record is Google Sheets, and **a Google Sheets cell holds at most 50,000 characters
while a playbook is allowed up to 60,000** — so the handbook text cannot be stored in one cell safely, and
splitting it across cells/rows is a storage redesign this task does not take on. Therefore:

- The upload → review → select-by-hash → preview **boundary is implemented and tested**, with selection
  **per session** (the client holds the reviewed text + hash and posts them to the preview, which re-derives
  and verifies the hash).
- **Durable cross-session selection is NOT implemented** and is not claimed. A reload loses the in-session
  selection; nothing is written to the Sheet.

## Independent recheck of `7f5d99b` (2026-10-01)

In network-disabled containers, the 22 focused Python tests and 4 Playbook component tests passed. The
local upload/review UI and follow-up preview are present, and the documented lack of durable selection is
honest. Two API-boundary gaps remain before calling it a selected/approved playbook workflow:

1. `POST /api/playbook/preview` accepts any caller-supplied `text` and matching `content_hash`; it has no
   record or verifiable token from `/api/playbook/review` or the founder's Select action. The existing route
   success test posts directly to `/preview` without reviewing or selecting first. A changed text plus its
   newly computed hash therefore bypasses the claimed “changed file must be reviewed and selected again”
   contract. The UI enforces that sequence for ordinary interaction, but the server does not. This is
   read-only, flag-gated local preview, so the impact is a misleading approval boundary rather than a send.
2. `/api/playbook/review` calls `upload.read()` without a bound and only checks `MAX_BYTES` afterwards in
   `playbook_extract.extract`. Unlike the import route's bounded read, the declared 5 MB cap does not bound
   upload allocation. `/api/playbook/preview` likewise accepts unbounded JSON text without the extractor's
   length check. Both routes need request-size and text-size enforcement before parsing/rendering.

The 50,000-character Sheets-cell limit explains why this implementation did not store playbook text in one
cell; it is not by itself a proof that durable selection is impossible. The existing architecture already
uses Drive for the production handbook. A future durable-selection design must decide how an approved
Drive-backed version and its hash are represented without silently changing production authority. No
product code or live service was changed by this recheck.

## Remediation of the recheck (2026-10-01, product-code change)

> **Partly superseded by "Remediation of the `78e47e0` recheck" below.** Point 1 here describes the
> token minted by `/review` as "selection evidence"; the follow-up recheck established it is **review**
> evidence only, and selection is now a separate explicit `/select` step. Point 2 here describes a bounded
> `read()` returning **422**; the size limit is now enforced **before parsing** and returns **413**. Read
> the later section for the current behaviour.

Both boundary gaps are closed; the preview stays flag-gated, local and read-only, and durable
cross-session selection is still **not** claimed. Verified in network-disabled containers: Python **1012
passed**, frontend **109 passed**, typecheck and build clean.

1. **The preview requires verifiable selection evidence; direct posting no longer works.**
   `outreach/playbook_select.py` mints an HMAC token (per-process secret) binding the reviewed content
   hash, the signed-in founder's email and a 30-minute expiry. `/api/playbook/review` returns it;
   `/api/playbook/preview` recomputes the hash from the posted text and the founder from the session and
   **refuses (403) unless the token verifies for that exact hash and founder and has not expired.** A caller
   cannot forge the token (no secret), cannot reuse it for changed text (the hash differs), cannot use
   another founder's token, and the selection dies on a server restart — it is local and time-bounded, never
   durable. *Regressions:* `test_playbook_select.py` (fresh/changed-hash/other-founder/expired/forged);
   `test_console_playbook.py` (a preview works only after a real review mints the token; a forged token →
   403; no token → 400; changed text + valid token → 403; another founder's token → 401/403). Verified over
   real HTTP in the harness: review → token → preview 200 "Hi Dana,"; forged → 403; none → 400; changed →
   403.
2. **Both routes are size-bounded before parsing.** `/review` reads at most `MAX_BYTES + 1` (5 MB) before
   anything is in memory and rejects a larger upload (422 `too_large`), mirroring the import route; `/preview`
   refuses a request body over `MAX_BYTES` (413) and text over `MAX_CHARS` (60,000) before hashing or
   rendering. *Regressions:* oversized multipart upload → 422, oversized JSON preview text → 413.

Also added: a positive extraction test using a **real PDF with selectable text** (a minimal valid PDF with a
correct xref, extracted by `pypdf`), alongside the existing DOCX text test and the PDF error-taxonomy tests.

Still **not** done and not claimed: durable cross-session selection (the Sheets 50,000-char cell limit vs a
60,000-char playbook remains the blocker; a durable design would have to represent an approved, Drive-backed
version and its hash without silently changing production authority). Nothing signed-in/deployed; the Drive
handbook stays authoritative for production; no Gmail draft, no send, no live write.

## Remediation of the `78e47e0` recheck (2026-10-01, product-code change)

Both recheck gaps are closed. The preview stays flag-gated, local and read-only; durable cross-session
selection is still **not** claimed. This section corrects two earlier descriptions: the token returned by
`/api/playbook/review` is **review evidence only, never an approval or a selection**, and the request-size
limit is now enforced **before parsing** (not the whole HTTP request "capped" by a bounded `read()` after
parsing has begun). Verified in network-disabled containers: Python **1019 passed** (39 focused playbook
tests), frontend **110 passed**, typecheck and build clean.

1. **Review and selection are separate server steps; a reviewed-but-never-selected version is refused.**
   `outreach/playbook_select.py` now binds a `purpose` ("review" or "select") into the HMAC payload
   alongside the content hash, the signed-in founder's email and a 30-minute expiry.
   - `/api/playbook/review` mints a **REVIEW** token and returns it as `review_token`. It is proof the
     server read and parsed this founder's exact text — nothing more. It does **not** open a preview.
   - The founder's explicit Select action reaches a new authenticated, flag-gated boundary,
     `POST /api/playbook/select`, which verifies the REVIEW token for the posted text and session founder
     and, only then, mints a **SELECT** token (time-bounded evidence for that exact reviewed hash).
   - `/api/playbook/preview` requires a **SELECT** token. A REVIEW token at `/preview` is refused (403), as
     are a forged token, changed text (the hash differs), another founder's token, and an expired token.

   Selection stays non-durable (the per-process secret dies on restart) and read-only; it is not connected
   to production drafting. *Regressions:* `test_playbook_select.py` (purpose REVIEW ≠ SELECT, changed hash,
   other founder, expired, forged); `test_console_playbook.py` (review returns a review token and no
   selection token; a review token at `/preview` → 403; `/review` → `/select` → `/preview` → 200 "Hi
   Dana,"; `/select` refuses a forged or changed review token → 403; direct `/preview` with no token → 400,
   forged → 403; a selection does not cross founders → 401/403). Verified over real loopback HTTP in the
   harness: review returns a review token only; preview with that review token → 403; select → 200 with the
   matching hash; preview with the selection token → 200; forged → 403; changed text + valid selection →
   403; oversized upload → 413 `too_large`.

2. **The request-size limit is enforced before multipart/JSON parsing, including requests with no usable
   Content-Length.** Each playbook route sets Werkzeug's per-request `request.max_content_length =
   MAX_BYTES` (5 MB) before touching `request.files` or `request.get_json()`, so an oversized body raises
   `RequestEntityTooLarge` during parsing and the route returns **413** (`too_large` on `/review`) rather
   than being buffered first. This holds even when Content-Length is absent or unusable (chunked/streamed),
   which a bounded `read()` could not guarantee. `/select` and `/preview` additionally cap the decoded text
   at `MAX_CHARS` (60,000) before hashing or rendering. Ordinary oversized files still get the clear
   extractor errors (`too_large`, `too_long`). *Regressions:* oversized multipart upload → 413 (with and
   without a usable Content-Length), oversized `/preview` JSON → 413, oversized `/select` JSON → 413.

Still **not** done and not claimed: durable cross-session selection — recorded separately in
`docs/decisions/playbook-durable-selection-2026-10-01.md`. Nothing signed-in/deployed; the Drive handbook
stays authoritative for production; no Gmail draft, no send, no live write.
